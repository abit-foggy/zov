# sklad — Zov Package and Toolchain Manager

`sklad` is the networked package, cache, and toolchain manager for the Zov programming language. It is written in Zov itself (`tools/sklad/main.zov`) and compiled by `zovc`.

## Architectural Boundary: `zovc` vs `sklad`

Zov enforces a strict architectural division of responsibilities:

1. **`zovc` is 100% offline.**
   - It is the local compiler and project driver.
   - It never accesses the network, never touches remote sockets, and has no concept of HTTP or Git protocols.
   - It compiles single files and local projects governed by `zov.toml`.
   - It resolves local filesystem dependencies (`path = "..."`), enforces editions (`--edition <year>`), and accepts mapped packages via `--pkg <name>=<local_path>`.
   - When encountering unmapped remote dependencies (`git` or `url`) without a local mapping, `zovc` safely aborts with an actionable error directing the user to `sklad fetch` or `sklad build`.

2. **`sklad` manages network, caching, and toolchains.**
   - It handles remote Git repositories (`git = "..."`), tarball archives (`url = "..."` + `sha256 = "..."`), and transitive dependency graphs.
   - It maintains the global package and toolchain cache under `$SKLAD_HOME` (`~/.sklad`).
   - It validates SHA-256 integrity checksums for downloaded archives.
   - It generates and maintains `sklad.lock` to ensure deterministic, reproducible builds.
   - Once dependencies are fetched and cached locally, `sklad` hands off compilation to the local offline `zovc` compiler by passing `--edition <ed>` and `--pkg <name>=<cached_path>` arguments.

```
+-------------------------------------------------------------+
|                           sklad                             |
|  - Git clone & checkout       - Tarball download & verify   |
|  - Dependency tree resolution - sklad.lock generation       |
|  - Toolchain management       - Cache in $SKLAD_HOME        |
+------------------------------+------------------------------+
                               |
                               | invokes with:
                               | --edition <ed>
                               | --pkg <name>=<cached_path>
                               v
+-------------------------------------------------------------+
|                     zovc (100% Offline)                     |
|  - Lexing & Parsing           - Semantic analysis (Sema)    |
|  - Borrow checking            - C code generation           |
|  - Local project build/run    - Strict C99 compilation      |
+-------------------------------------------------------------+
```

## `zov.toml` Manifest Specification

Every Zov package is configured by a `zov.toml` manifest located in the project root:

```toml
[package]
name = "my_service"
version = "0.1.0"
edition = "2026"
zovc = "0.9.0"
entry = "src/main.zov"

[dependencies]
# Local path dependency (supported directly by offline zovc)
local_util = { path = "../local_util" }

# Remote Git dependency (fetched and pinned by sklad)
web_router = { git = "https://github.com/example/web_router.git", rev = "v1.2.0" }

# Remote URL tarball with cryptographic checksum (fetched and verified by sklad)
json_codec = { url = "https://example.com/releases/json_codec-0.4.0.tar.gz", sha256 = "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855" }
```

### Fields

- `package.name`: Unique identifier for the package.
- `package.version`: Semver version string (e.g. `"0.1.0"`).
- `package.edition`: Language edition year (e.g. `"2026"`). Rejection occurs if unsupported (`error[E0903]`).
- `package.zovc`: Minimum required compiler version. If `zovc` is older, build aborts with an actionable error.
- `package.entry`: Optional path to entry point (defaults to `src/main.zov` or `main.zov`).
- `dependencies.<name>`:
  - `path = "..."`: Local filesystem path relative to the manifest directory.
  - `git = "..."`: Remote or local Git repository URL.
  - `rev = "..."` or `tag = "..."`: Git branch, tag, or commit hash.
  - `url = "..."`: HTTP/HTTPS or local tarball URL (`.tar.gz` or `.tgz`).
  - `sha256 = "..."`: Cryptographic SHA-256 hash required for URL tarball verification.

## `sklad.lock` Lockfile

Running `sklad fetch` or `sklad build` generates or updates `sklad.lock` in the project root. This ensures reproducible builds across machines and environments.

Example `sklad.lock`:

```toml
# This file is automatically generated by sklad.
# Do not edit manually.

[[package]]
name = "web_router"
version = "1.2.0"
source = "git"
git = "https://github.com/example/web_router.git"
commit = "d6a8f192b67823e1c6a281e05d048d0cf4893812"

[[package]]
name = "json_codec"
version = "0.4.0"
source = "url"
url = "https://example.com/releases/json_codec-0.4.0.tar.gz"
sha256 = "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
```

## Cache Layout (`$SKLAD_HOME`)

By default, `sklad` stores cached dependencies, downloaded archives, and installed toolchains under `~/.sklad`. This can be customized by setting the `SKLAD_HOME` environment variable.

Directory hierarchy:

```
$SKLAD_HOME/
├── cache/
│   ├── git/
│   │   └── <pkg>-<hash>/      # Cloned Git repository checked out to pinned revision
│   ├── dl/
│   │   └── <pkg>-<hash>.tar.gz # Downloaded archive files
│   └── tar/
│       └── <pkg>-<hash>/      # Unpacked archive contents
└── toolchains/
    └── <version>/             # Installed zovc/sklad toolchains
```

## CLI Commands

### `sklad init [dir]`
Initializes a new Zov package. If `dir` is omitted, initializes the current working directory. Delegates directly to `zovc init`.

### `sklad fetch`
Reads `zov.toml`, downloads remote dependencies (Git and URL), verifies SHA-256 integrity, resolves transitive dependencies, caches them in `$SKLAD_HOME`, and generates `sklad.lock`.

### `sklad add <name> [options]`
Appends a dependency to `zov.toml`:
- `--git <url> [--rev <rev>]`
- `--url <url> --sha256 <hash>`
- `--path <dir>`

### `sklad check`
Fetches dependencies if needed, then invokes `zovc check` with `--pkg <name>=<cached_path>` flags and `--edition`.

### `sklad build [--release] [--offline]`
Fetches dependencies (unless `--offline` is specified), then invokes `zovc build` with `--pkg` mappings to build the executable into `target/`.

### `sklad run [--release] [--offline] [-- <run-args>...]`
Builds the project and executes the binary, forwarding arguments and standard input.

### `sklad tree`
Visualizes the resolved dependency hierarchy in ASCII format:

```text
my_service v0.1.0
├── local_util (path: ../local_util)
├── web_router (git: https://github.com/example/web_router.git @ d6a8f19)
└── json_codec (url: https://example.com/releases/json_codec-0.4.0.tar.gz)
```

### `sklad lock`
Refreshes and verifies the validity of `sklad.lock` against `zov.toml`.

### `sklad toolchain [status|list|install <version>]`
- `status`: Displays active `zovc` compiler version and project minimum requirement.
- `list`: Lists installed toolchain versions under `$SKLAD_HOME/toolchains`.
- `install <version>`: Downloads and installs an official `zovc` toolchain release.

### `sklad version`
Displays version information for `sklad` and the active `zovc` compiler.
